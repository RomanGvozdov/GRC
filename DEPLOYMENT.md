# Інструкція з розгортання GRC-системи

Покрокова інструкція для першого розгортання, оновлення, увімкнення AI, резервного
копіювання та типових проблем. Загальний опис системи — [README.md](README.md),
стан модернізації — [MODERNIZATION_PROGRESS.md](MODERNIZATION_PROGRESS.md).

---

## 1. Вимоги до сервера

| Компонент | Мінімум | Рекомендовано |
|---|---|---|
| ОС | Linux x86_64 (Ubuntu 22.04+/Debian 12+) | те саме |
| CPU | 2 vCPU | 4 vCPU |
| RAM (без AI) | 4 ГБ | 8 ГБ |
| RAM (з локальним AI, модель 7–8B) | 16 ГБ | 24 ГБ (або GPU) |
| Диск | 20 ГБ SSD | 50 ГБ (докази, бекапи, AI-моделі ~10 ГБ) |
| ПЗ | Docker Engine 24+ і **Docker Compose V2** (`docker compose`, не `docker-compose`) | |

Перевірка Compose V2:

```bash
docker compose version   # має вивести v2.x
```

> Якщо команда `docker compose` невідома — встановіть плагін
> `docker-compose-plugin` з офіційного репозиторію Docker або standalone-бінарник
> Compose V2. Docker зі snap часто конфліктує — за проблем видаліть snap-версію
> і поставте Docker з офіційного репозиторію.

Мережа: система розгортається **у внутрішньому контурі (КСЗІ)**. Доступ в
інтернет потрібен лише на етапі збірки образів (Docker Hub) і разового
завантаження AI-моделей; далі система працює автономно.

## 2. Підготовка

```bash
# 1) Отримати код (гілка з поточною версією)
git clone <URL-репозиторію> grc && cd grc
git checkout claude/awesome-planck-76efci   # або main після злиття

# 2) Створити конфіг із шаблона
cp .env.example .env
```

Заповнити в `.env` **обов'язково**:

| Змінна | Що вказати |
|---|---|
| `POSTGRES_PASSWORD` | довільний надійний пароль БД |
| `SECRET_KEY` | згенерувати: `openssl rand -hex 32` |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_FULL_NAME` | перший адміністратор (створюється один раз, коли БД порожня; пароль ≥12 символів, не словниковий) |
| `HTTP_PORT` | порт веб-інтерфейсу (типово 80) |

Опційно (можна лишити порожніми і заповнити пізніше): `SMTP_*` + `BASE_URL`
(email-сповіщення), `SLACK_WEBHOOK_URL` / `TELEGRAM_*` (дайджест у канал),
`DIGEST_HOUR`, блок `AI_*` (див. розділ 5).

> **Безпека:** файл `.env` містить секрети, він у `.gitignore` — ніколи не
> комітьте його і не копіюйте за межі сервера. Доступ: `chmod 600 .env`.

## 3. Перше розгортання

```bash
docker compose up -d --build
docker compose logs -f backend     # спостерігати старт
```

Що відбувається автоматично при старті backend:
1. **Міграції** — `alembic upgrade head` (ревізії `0001`–`0008`): створюється вся
   схема БД. На наступних оновленнях застосовуються лише нові ревізії, дані не
   втрачаються.
2. **Сідинг** — перший адміністратор (з `ADMIN_*`), категорії ризиків, каталоги
   вимог: НД ТЗІ 3.6-006-24 (1189 заходів + 288 ODP-параметрів), NIST 800-53 EN
   (1189), ISO 27001 (93), NIST starter (171); три базові профілі НД ТЗІ як
   baselines (конфіденційний 84 / службовий 97 / реєстровий 119).
3. Планувальник сповіщень (APScheduler).

Успішний старт у логах: рядки про застосовані міграції та
`Імпортовано каталог …`, без traceback-ів.

**Перший вхід:** відкрийте `http://<сервер>:<HTTP_PORT>/`, увійдіть з
email/паролем адміністратора з `.env`. Система запропонує налаштувати
**обов'язковий 2FA**: відскануйте QR-код застосунком (Google Authenticator,
Aegis тощо) і **збережіть резервні коди** — це єдиний спосіб увійти при втраті
телефона.

### Швидка перевірка (smoke-тест)

```bash
curl -s http://localhost:${HTTP_PORT:-80}/api/health   # {"status":"ok"}
```

В UI: «Каталоги» — 4 каталоги; «Базові набори» — 3 baselines (84/97/119);
створіть тестову ІКС → «Категоризувати» → система пропонує baseline.

## 4. TLS і доступ по мережі

Контейнер frontend слухає HTTP. Для продуктивної експлуатації:

- опублікуйте `HTTP_PORT` лише на localhost (`127.0.0.1:8080:80` у
  `docker-compose.yml`) і поставте попереду TLS-термінатор (nginx або Caddy
  з сертифікатом організації), **або**
- якщо доступ лише з довіреної внутрішньої мережі — відкрийте порт на потрібному
  інтерфейсі та обмежте його файрволом до сегмента користувачів.

## 5. AI-функції (опційно)

За замовчуванням AI вимкнено, система повноцінна без нього (AI-кнопки повертають
зрозумілу помилку 503). **Для КСЗІ — лише локальна модель**, дані не покидають
периметр.

```bash
# 1) У .env: AI_ENABLED=true (моделі за замовчуванням: qwen2.5:7b + bge-m3)
# 2) Підняти стек із вбудованим Ollama (профіль "ai"):
docker compose --profile ai up -d --build
# 3) Один раз завантажити моделі (потрібен інтернет або перенесіть файли моделей):
docker compose exec ollama ollama pull qwen2.5:7b
docker compose exec ollama ollama pull bge-m3
```

Перевірка: в UI (адміном) `GET /api/ai/status` → `enabled: true`,
`vector_ready: true`. Потім «AI-пошук» → **«Переіндексувати»** (разова
індексація каталогів/контролів/політик у векторне сховище; повторюйте після
великих змін даних).

Після цього працюють: AI-пошук (Q&A), «✨ AI-чернетка» в SSP, «↔ AI» мапінг
каталогів, «AI: рекомендувати контролі» на ризику, «✨ AI RMF» bootstrap на ІКС.

Зауваження:
- Порт Ollama назовні не публікується — доступ лише з backend.
- `AI_EMBED_DIM` (1024 для bge-m3) фіксується при першому створенні векторної
  таблиці — задайте під свою embed-модель **до** першої індексації.
- Зовнішній OpenAI-сумісний сервер замість вбудованого Ollama: вкажіть його URL
  в `AI_BASE_URL` і запускайте без профілю `ai`.

## 6. Оновлення системи

```bash
# 1) Резервна копія БД (обов'язково перед оновленням)
docker compose exec db pg_dump -U grc grc > backup_$(date +%F).sql

# 2) Оновлення
git pull
docker compose up -d --build        # з AI: docker compose --profile ai up -d --build
docker compose logs -f backend      # переконатися, що міграції пройшли
```

Міграції та оновлення сід-даних застосовуються автоматично. Правила оновлення
каталогів: каталог оновлюється до нової версії сід-файлу **лише якщо на ньому ще
не побудовано профілів** (захист даних); ODP-параметри в наявні каталоги
досіюються окремим ідемпотентним бекфілом і працюють навіть якщо профілі вже є.

## 7. Резервне копіювання та відновлення

Що бекапити:

| Дані | Де | Як |
|---|---|---|
| База даних | том `pgdata` | `docker compose exec db pg_dump -U grc grc > backup_$(date +%F).sql` |
| Файли доказів | том `uploads` | `docker run --rm -v grc_uploads:/d -v $PWD:/b alpine tar czf /b/uploads_$(date +%F).tgz -C /d .` |
| Конфіг | `.env` | копія в захищене сховище |
| AI-моделі (опц.) | том `ollama` | не критично — можна перезавантажити |

Рекомендація: щоденний `pg_dump` за cron + зберігання копій поза сервером.

Відновлення:

```bash
docker compose up -d db
cat backup_2026-06-25.sql | docker compose exec -T db psql -U grc grc
docker compose up -d
```

## 8. Експлуатаційні операції

- **Скидання пароля користувача:** адмін → «Користувачі» → «Скинути пароль»
  (усі сесії користувача анулюються). Скидання 2FA — там само.
- **Єдиний адмін втратив доступ:** відновлення через БД (скидання хеша) —
  звертайтесь до супроводу; профілактика — тримайте **двох** адміністраторів.
- **API-токени для інтеграцій** (сканери → авто-докази ConMon): «API-токени» →
  створити від користувача з правом «контролі: запис», далі
  `POST /api/ingest/evidence` з заголовком `Authorization: Bearer grc_...`.
- **Логи:** `docker compose logs backend|db|frontend|ollama`.
- Повний журнал дій користувачів — в UI, «Журнал дій» (незмінний).

## 9. Типові проблеми

| Симптом | Причина і рішення |
|---|---|
| `unknown shorthand flag: 'd'` на `docker compose up -d` | Стоїть Compose V1 або snap-docker. Встановіть Compose V2 (див. розділ 1). |
| Backend падає на старті: `POSTGRES_PASSWORD`/`SECRET_KEY` | Не заповнений `.env`. Заповніть і `docker compose up -d`. |
| Rate limit Docker Hub при збірці | Повторіть пізніше, або `docker login`, або перенесіть образи з іншої машини (`docker save/load`). |
| Каталог НД ТЗІ лишився «тонким» після оновлення | На ньому вже є профілі — авто-refresh свідомо пропущено. Якщо профілі тестові: видаліть каталог в UI і перезапустіть backend (пересіється повний). |
| В «Каталогах» висить старий `nd-tzi-3-6-006-24-full` (315) | Спадок старої версії — видаліть вручну в UI, він не використовується. |
| `/api/ai/status`: `vector_ready: false` | БД не pgvector-образ або розширення не створилось: перевірте, що сервіс db зібраний з `pgvector/pgvector:pg16` (том `pgdata` сумісний зі звичайним postgres:16), і перегляньте логи міграції `0003`. |
| AI-відповіді порожні/помилка після ввімкнення | Не завантажені моделі в Ollama (`ollama pull …`) або не виконано «Переіндексувати». |
| Листи не надходять | Email вимкнені, поки не задано `SMTP_HOST`; перевірте також `BASE_URL` і логи backend о годині дайджесту. |

## 10. Відкат

```bash
docker compose down
git checkout <попередній-коміт-або-тег>
cat backup_<дата>.sql | docker compose exec -T db psql -U grc grc   # якщо міграції вже змінили схему
docker compose up -d --build
```

Міграції вперед-сумісні й ідемпотентні, але відкат схеми назад офіційно не
підтримується — стандартний шлях відкату: **відновлення БД з дампа** + попередня
версія коду.
