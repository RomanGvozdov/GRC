# STATUS: GRC-система — зведений стан функціоналу

> Документ для незалежного аналізу. Самодостатній: описує призначення, архітектуру,
> повний перелік реалізованого функціоналу, ключові проєктні рішення, відомі
> обмеження та невиконані пункти. Стан на 12.06.2026.

## 1. Що це

Внутрішня on-premise GRC-система (Governance, Risk & Compliance) для команди
безпеки/комплаєнсу однієї компанії (~20 користувачів). Інтерфейс і звіти —
українською. Повна специфікація вимог — у `SPEC.md` репозиторію.

**Стек:** Python 3.12 / FastAPI / SQLAlchemy 2 / PostgreSQL 16 (SQLite в тестах);
React 18 / TypeScript / Mantine 7 / Vite; WeasyPrint (PDF); APScheduler (планувальник);
розгортання — Docker Compose (db + backend + nginx), TLS очікується на зовнішньому
термінаторі. Архітектура — модульний моноліт, REST API з OpenAPI (`/docs`).

**Стан:** усі 4 фази roadmap + позапланова фаза «ІКС» реалізовані, запушені в гілку
`claude/awesome-planck-76efci`, розгорнуті користувачем на власному сервері.
**39 інтеграційних тестів** (pytest) — зелені. Фронтенд збирається без помилок TS.

> **Триває модернізація** (NIST 800-53 цільові профілі + RMF + OSCAL + AI) —
> див. ТЗ у `docs/` та поточний прогрес/чергу в **`MODERNIZATION_PROGRESS.md`**.
> Уже зроблено: схема під Alembic; «Каталог 2.0» (enhancements + ODP-параметри);
> AI-інфраструктура (pgvector + провайдер LLM + провенанс, вимкнено за замовч.).

## 2. Реалізований функціонал

### 2.1 Автентифікація та користувачі — ✅
- Локальні акаунти; обов'язковий TOTP (RFC 6238) для всіх: перший вхід → QR-код →
  резервні коди (показуються один раз, у БД — SHA-256).
- JWT access (15 хв) + refresh (7 діб); `token_version` для «вийти з усіх пристроїв»;
  блокування акаунта після 5 невдалих спроб (15 хв); Argon2id; TOTP-секрети
  шифруються в БД (Fernet від SECRET_KEY); словник поширених паролів
  (~200 основ × типові суфікси), мінімум 12 символів.
- Перший адміністратор створюється з env при порожній БД.

### 2.2 RBAC — ✅
- 4 вбудовані ролі: адміністратор, GRC-менеджер, виконавець, читач.
- Модель дозволів: 8 модулів (risks, controls, frameworks, audits, policies,
  reports, audit_log, admin) × 4 рівні (none < read < write < manage).
  `write` = редагування лише призначених користувачеві об'єктів.
- Кастомні ролі (матриця модуль × рівень) повністю заміщують вбудовану роль
  користувача. `/auth/me` повертає ефективні дозволи; UI ховає недоступне.
- API-токени для інтеграцій (`grc_…`, SHA-256 у БД, термін дії, відкликання,
  last_used) — діють від імені користувача з його дозволами.

### 2.3 Системи (ІКС) — ✅ (позапланове розширення)
- Реєстр ІКС: код SYS-XXX, критичність, статус, відповідальний,
  **тип базового профілю** за НД ТЗІ 3.6-006-24 (конфіденційна / службова інформація).
- Глобальний перемикач контексту в шапці: «Вся організація» або конкретна ІКС.
  Правило фільтрації всюди: об'єкти системи + загальноорганізаційні (без прив'язки).
- Ризики, аудити, політики прив'язуються до кількох ІКС (m2m).

### 2.4 Управління ризиками — ✅
- Реєстр RISK-XXX: категорія (довідник), активи, джерело загрози, вразливість,
  відповідальний, дата перегляду, системи; статуси: чернетка → ідентифікований →
  оцінений → в обробці → моніториться → закритий.
- Якісна матриця 5×5: притаманна та залишкова оцінки, історія оцінок (хто/коли),
  рівні: 1–4 низький, 5–9 середній, 10–14 високий, 15–25 критичний.
- План обробки: дії з виконавцями, дедлайнами, статусами
  (відкрита → в роботі → виконана → перевірена).
- Стратегії: зменшити/прийняти/уникнути/передати. Прийняття ризику з рівнем ≥10
  вимагає ролі менеджера + коментаря; фіксується хто/коли затвердив.
- Зв'язок ризик ↔ контролі (m2m); створення ризику зі знахідки аудиту.

### 2.5 Комплаєнс — ✅
- Каталоги вимог: ISO 27001:2022 Annex A (93 вимоги, українською, seed),
  NIST SP 800-53 Rev.5 (базовий набір 171 контроль, англійською, seed),
  кастомні каталоги (CRUD адміном) + JSON-імпорт повних каталогів.
- Вимоги можуть мати **профілі** (confidential/service) — для профільних
  каталогів типу НД ТЗІ; вимога без профілів застосовна до всіх.
- Контролі CTRL-XXX: назва, тип (превентивний/детективний/коригувальний),
  відповідальний, мапінг на вимоги будь-яких фреймворків (m2m).
- **Матриця впроваджень**: статус (не впроваджено/частково/впроваджено/не
  застосовно), NA-обґрунтування, періодичність і дата перевірки та докази
  (файли/посилання) ведуться окремо для кожної пари «контроль × ІКС»
  (або «вся організація»). Зведений статус контролю — найгірший серед впроваджень.
- Семантика контексту: в ІКС специфічне впровадження має пріоритет над
  загальноорганізаційним; «вся організація» — консервативно найгірший статус.
- Gap-аналіз по фреймворку: покриття кожної вимоги
  (покрито/частково/не покрито/не застосовно), % відповідності; у контексті ІКС
  враховує профіль системи (незастосовні профільні вимоги виключаються).

### 2.6 Аудити — ✅
- Аудити AUD-XXX: тип (внутрішній/зовнішній), область, період, аудитор
  (внутрішній користувач або зовнішній текстом), системи, статуси:
  запланований → триває → звіт → закритий.
- Чек-листи: автогенерація з вимог фреймворка + ручні пункти; результат
  (відповідає/частково/не відповідає/не застосовно) + коментар.
- Знахідки FND-XXX: критичність (4 рівні), вбудована коригувальна дія
  (відповідальний, дедлайн, статус), створення ризику зі знахідки зі зв'язком.

### 2.7 Політики та документи — ✅
- Життєвий цикл: чернетка → на погодженні → затверджена → діюча →
  переглядається → архівна.
- Версіонування: нова редакція успадковує текст, попередні в історії.
- Погодження кількома погоджувачами: відхилення (з коментарем) повертає в
  чернетку; погодження всіма → затверджена; активація менеджером.
- Ознайомлення: призначення користувачів на діючу версію, фіксація дати/часу
  підтвердження, прогрес N/M; індикатори «очікує вашого погодження/ознайомлення».
- Текст у Markdown або вкладений файл; зв'язки з контролями та ІКС.

### 2.8 «Мої задачі» — ✅
- Єдина сторінка + лічильник у меню: дії з обробки, коригувальні дії,
  погодження, ознайомлення, прострочені перегляди моїх ризиків/контролів/політик.
  Прострочені згори, сортування за дедлайном.

### 2.9 Звітність — ✅
- Дашборд (поважає контекст ІКС): heat map 5×5, ризики за рівнями/статусами,
  топ-5 ризиків, % відповідності по фреймворках, лічильники прострочень
  (перегляди ризиків/контролів/політик, дії).
- PDF (WeasyPrint, українською): реєстр ризиків, gap-аналіз, звіт аудиту
  (чек-лист + знахідки), Statement of Applicability (з NA-обґрунтуваннями;
  по системах — окремий рядок на впровадження). Gap/SoA враховують контекст ІКС.
- Excel/CSV-експорт ризиків (з системами) і контролів (рядок на впровадження);
  CSV з BOM для кирилиці.

### 2.10 Імпорт з Excel — ✅
- Шаблони .xlsx для ризиків і контролів (заголовки = експортні).
- Двокроковий процес: dry-run з помилками по рядках (рядок/причина) → імпорт
  валідних. Автостворення категорій та ІКС; відповідальний за email; вимоги
  кодами через кому; контроль із кількома системами → впровадження на кожну.

### 2.11 Сповіщення — ✅
- Email (SMTP, опційно): миттєві при призначеннях (ризик, дія, знахідка,
  погодження, рішення власнику, ознайомлення) + щоденний дайджест прострочень
  кожному відповідальному (APScheduler, година налаштовується, Europe/Kyiv).
- Slack (webhook) та/або Telegram (бот): зведення дайджесту в канал.
- Усе best-effort у фонових потоках; вимкнено, поки не задано SMTP_HOST.

### 2.12 Наскрізне — ✅
- Незмінний журнал дій (хто/що/коли/деталі) на всі мутації; доступ за дозволом.
- Коментарі до ризиків/контролів/аудитів/знахідок/політик (потрібен write).
- Пошук і фільтри в реєстрах; вкладення до 25 МБ (налаштовується).
- Авто-міграція схеми при старті (нові таблиці/колонки + перенесення даних
  старих схем без втрат); Alembic-каркас для майбутніх ревізій.

## 4. Відомі обмеження та технічні борги

1. **Невиконане зі SPEC:** англійська локалізація UI (рядки захардкоджені
   українською, i18n-файлів немає); кількісна оцінка ризиків FAIR (у SPEC опційна).
2. **Каталог НД ТЗІ 3.6-006-24 наповнено**: 98 заходів захисту (за кодами
   NIST 800-53) з двох базових профілів — конфіденційна (84) та службова (97),
   83 спільних; для 11 заходів зберігаються окремі редакції тексту під профіль.
   Сідиться автоматично; gap-аналіз/SoA фільтрують за профілем ІКС. Секція
   «Посилені та додані заходи» (Дод.1) у вихідних профілях порожня — за потреби
   наповнюється під конкретну ІКС.
3. Схема БД керується Alembic: при старті застосовується `upgrade head`
   (базова ревізія `0001` idempotent для вже розгорнутих БД). Подальші зміни —
   explicit-ревізіями.
4. Збережені фільтри (SPEC 3.6) не реалізовані; фільтри живуть лише в стані сторінки.
5. Excel-експорт ігнорує активні фільтри UI (вивантажує все).
6. Брендування PDF (логотип компанії) не зроблено — плейсхолдер «GRC · Конфіденційно».
7. Docker-стек не проганявся end-to-end у CI (Docker Hub rate limit у середовищі
   розробки); користувач розгорнув на сервері вручну — працює.
8. Лічильник «Мої задачі» в меню оновлюється лише при перезавантаженні сторінки.
9. Rate limiting на логін — на рівні nginx (10 r/m) + блокування акаунта; на інших
   ендпоїнтах немає.
10. E2E/фронтенд-тестів немає (тільки 30 інтеграційних API-тестів); навантажувальних
    тестів немає (цільове навантаження ~20 користувачів).
11. Видалення об'єктів фізичне (не soft-delete); історія залишається лише в audit log.
12. Один upload-каталог для всіх файлів (томи docker); антивірусної перевірки
    завантажень немає.

## 5. Що варто проаналізувати (підказки для рецензента)

- Семантика матриці впроваджень: «найгірший статус» для організації та
  «специфічне > загальне» для ІКС — чи відповідає очікуванням аудиторів ISO/КСЗІ?
- Модель RBAC: чи достатньо рівня write=«лише свої об'єкти» без object-level ACL?
- Потік погодження політик: відхилення скидає всі погодження (повернення в
  чернетку) — чи потрібне часткове перепогодження?
- Безпека: JWT у localStorage (XSS-ризик) vs httpOnly cookie; відсутність CSRF
  не критична для Bearer-схеми, але варто перевірити.
- Життєвий цикл ознайомлень при новій версії політики: призначення робляться
  заново вручну — чи автоматизувати перенесення списку?
- Прогалини відносно зрілих GRC (Archer, ServiceNow GRC): workflow-движок,
  делегування, вкладені організації, кампанії атестації доступів.
