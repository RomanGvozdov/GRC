# SPEC: GRC-система

Специфікація вимог до внутрішньої системи управління ризиками, комплаєнсом, аудитами та політиками (Governance, Risk & Compliance).

## 1. Загальний опис

### 1.1 Призначення

Внутрішній інструмент для команди безпеки/комплаєнсу однієї компанії (до ~20 користувачів). Система централізує:

- **Управління ризиками** — реєстр ризиків, оцінка, плани обробки, моніторинг.
- **Комплаєнс** — відповідність стандартам, контролі, мапінг вимог, gap-аналіз.
- **Аудити** — планування, чек-листи, знахідки (findings), коригувальні дії.
- **Політики та документи** — життєвий цикл політик: створення, погодження, версіонування, ознайомлення співробітників.

### 1.2 Цільові стандарти та регуляції

| Фреймворк | Використання |
|---|---|
| ISO/IEC 27001 (Annex A) | Основний каталог контролів, методологія ISMS |
| NIST SP 800-53 | Додатковий каталог контролів, мапінг на ISO 27001 |
| Українські вимоги (НД ТЗІ, КСЗІ, законодавство про захист інформації) | Локальні вимоги, кастомний каталог |

Система має підтримувати **декілька фреймворків одночасно** з мапінгом «один контроль ↔ багато вимог різних фреймворків».

### 1.3 Ключові рішення

- **Розгортання:** on-premise (Docker Compose), дані не покидають інфраструктуру компанії.
- **Стек:** Python (FastAPI) + React/TypeScript + PostgreSQL.
- **Автентифікація:** локальні акаунти (email/пароль) + обов'язкова 2FA (TOTP).
- **Мова інтерфейсу та звітів:** українська.
- **Оцінка ризиків:** якісна матриця 5×5 (ймовірність × вплив).
- **Інтеграції:** відсутні в MVP, передбачені в roadmap.
- **Ролі:** фіксований набір у MVP, гнучкий RBAC у roadmap.

## 2. Користувачі та ролі

Фіксовані ролі MVP:

| Роль | Права |
|---|---|
| **Адміністратор** | Керування користувачами та налаштуваннями, повний доступ до всіх модулів |
| **GRC-менеджер** | Створення/редагування ризиків, контролів, аудитів, політик; призначення відповідальних; затвердження |
| **Виконавець** | Робота з призначеними йому об'єктами: оновлення статусів ризиків, виконання коригувальних дій, надання доказів (evidence) |
| **Читач** | Перегляд усіх даних і звітів без права редагування |

Принципи:
- Кожен об'єкт (ризик, контроль, знахідка, політика) має одного **відповідального (owner)**.
- Виконавець бачить усе, але редагує лише призначене йому.
- Усі зміни фіксуються в журналі аудиту (audit log) — хто, що, коли.

## 3. Функціональні вимоги

### 3.1 Модуль «Управління ризиками»

**Реєстр ризиків.** Кожен ризик містить:
- ідентифікатор (автогенерований, напр. `RISK-001`), назву, опис;
- категорію (довідник: інформаційна безпека, операційні, юридичні, фінансові, кадрові — редагований адміністратором);
- активи/процеси, яких стосується ризик;
- джерело загрози та вразливість;
- відповідального (owner) та дату наступного перегляду;
- пов'язані контролі (з модуля комплаєнсу);
- статус: `чернетка → ідентифікований → оцінений → в обробці → моніториться → закритий`.

**Оцінка ризиків — якісна матриця 5×5:**
- Ймовірність: 1 (дуже низька) … 5 (дуже висока).
- Вплив: 1 (незначний) … 5 (критичний).
- Рівень ризику = ймовірність × вплив, з відображенням на шкалу:
  - 1–4 — низький (зелений), 5–9 — середній (жовтий), 10–14 — високий (помаранчевий), 15–25 — критичний (червоний).
- Оцінка фіксується двічі: **притаманний ризик** (до контролів) та **залишковий ризик** (після контролів).
- Історія оцінок зберігається (дата, оцінювач, значення) для відстеження динаміки.

**Обробка ризиків.** Для кожного ризику обирається стратегія: *зменшити / прийняти / уникнути / передати*. Стратегія «зменшити» вимагає плану обробки — переліку дій із відповідальними та дедлайнами. Прийняття ризику вище порогового рівня (налаштовується, за замовчуванням «високий») вимагає явного затвердження GRC-менеджером із коментарем.

**Моніторинг.** Дашборд: heat map 5×5, топ ризиків, кількість за статусами, прострочені перегляди.

### 3.2 Модуль «Комплаєнс»

**Каталоги вимог.** Система постачається з імпортованими каталогами:
- ISO 27001 Annex A (93 контролі, версія 2022);
- NIST SP 800-53 (можливість обрати підмножину сімейств);
- кастомний каталог для українських вимог (НД ТЗІ тощо), який наповнює адміністратор.

**Контролі.** Внутрішній реєстр контролів компанії. Кожен контроль:
- назва, опис, тип (превентивний/детективний/коригувальний), відповідальний;
- мапінг на вимоги одного чи кількох фреймворків (many-to-many);
- статус впровадження: `не впроваджено / частково / впроваджено / не застосовно` (з обґрунтуванням для «не застосовно» — основа для Statement of Applicability за ISO 27001);
- докази впровадження (evidence): прикріплені файли, посилання, дата актуальності;
- періодичність перевірки та дата наступної перевірки.

**Gap-аналіз.** Для обраного фреймворка — звіт: які вимоги покриті контролями, статус впровадження, % відповідності, перелік прогалин.

### 3.3 Модуль «Аудити»

**Планування.** Аудит має назву, тип (внутрішній/зовнішній), область (scope: обрані фреймворки/контролі/підрозділи), період, аудитора, статус: `запланований → триває → звіт → закритий`.

**Чек-листи.** Формуються з вимог обраного фреймворка або вручну. Кожен пункт: відповідність (`відповідає / частково / не відповідає / не застосовно`), коментар, докази.

**Знахідки (findings).** Кожна знахідка:
- критичність (низька/середня/висока/критична), опис, пов'язаний контроль/вимога;
- **коригувальна дія**: відповідальний, дедлайн, статус (`відкрита → в роботі → виконана → перевірена`);
- знахідка може породжувати новий ризик у реєстрі (зв'язок зберігається).

### 3.4 Модуль «Політики та документи»

**Життєвий цикл:** `чернетка → на погодженні → затверджена → діюча → переглядається → архівна`.

- Версіонування: кожна зміна затвердженої політики створює нову версію; попередні доступні в історії.
- Погодження: один або кілька погоджувачів; політика стає діючою після затвердження всіма.
- Періодичний перегляд: дата наступного перегляду, прострочення підсвічуються.
- **Ознайомлення:** GRC-менеджер призначає перелік користувачів, які мають підтвердити ознайомлення; система фіксує дату/час підтвердження; звіт про стан ознайомлення.
- Зберігання файлів: вкладення (PDF/DOCX) або текст у системі (Markdown-редактор).
- Зв'язки: політика ↔ контролі, які вона реалізує.

### 3.5 Звітність (наскрізна)

- **Дашборди** (головна сторінка + по модулях): heat map ризиків, % відповідності по фреймворках, статус коригувальних дій, прострочені перегляди політик і контролів.
- **PDF-звіти** (українською, з логотипом компанії): реєстр ризиків, звіт про стан комплаєнсу (gap-аналіз), звіт за результатами аудиту, Statement of Applicability.
- **Excel/CSV-експорт** усіх реєстрів (ризики, контролі, знахідки, політики) з урахуванням активних фільтрів.

### 3.6 Спільні можливості

- Журнал аудиту (audit log): незмінний запис усіх створень/змін/видалень з автором і часовою міткою; перегляд доступний адміністратору та читачам.
- Пошук і фільтрація в усіх реєстрах; збережені фільтри.
- Коментарі до будь-якого об'єкта.
- Вкладення файлів (ліміт розміру налаштовується, за замовчуванням 25 МБ).
- Довідники (категорії ризиків, підрозділи, активи) керуються адміністратором.

## 4. Нефункціональні вимоги

### 4.1 Безпека

- Автентифікація: email/пароль + обов'язковий TOTP (RFC 6238); резервні коди відновлення.
- Політика паролів: мінімум 12 символів, перевірка проти словника витоків (локальний список).
- Сесії: JWT із коротким TTL + refresh-токени; вихід з усіх пристроїв.
- Блокування акаунта після 5 невдалих спроб входу (розблокування адміністратором або за часом).
- Паролі — Argon2id; чутливі дані (TOTP-секрети) шифруються у БД.
- HTTPS обов'язково (TLS термінується на reverse proxy, входить у Docker Compose).
- Захист від OWASP Top 10: параметризовані запити (ORM), CSRF-захист, security headers, rate limiting на автентифікацію.

### 4.2 Розгортання та експлуатація

- Один `docker-compose.yml`: backend, frontend (static + nginx), PostgreSQL, reverse proxy.
- Конфігурація через змінні середовища (`.env.example` у репозиторії).
- Міграції БД автоматичні при старті (Alembic).
- Бекап: скрипт `pg_dump` за розкладом + документація з відновлення.
- Цільове залізо: 1 ВМ, 4 GB RAM достатньо для 20 користувачів.

### 4.3 Продуктивність і надійність

- До 20 одночасних користувачів; відповідь UI ≤ 1 с для типових операцій.
- Обсяг даних: тисячі ризиків/контролів — без спеціальних вимог до масштабування.
- Доступність: робочі години; планові вікна обслуговування допустимі.

### 4.4 Локалізація

- Інтерфейс, довідники, PDF-звіти — українською.
- Дати у форматі `ДД.ММ.РРРР`, часовий пояс Europe/Kyiv (налаштовується).
- Архітектурно тексти UI виносяться в файли локалізації (i18n), щоб додавання англійської пізніше не вимагало переробки.

## 5. Технічна архітектура

| Шар | Технологія |
|---|---|
| Backend | Python 3.12+, FastAPI, SQLAlchemy 2 + Alembic, Pydantic |
| Frontend | React 18+, TypeScript, Vite; UI-кіт — на розсуд виконавця (Mantine/MUI) |
| БД | PostgreSQL 16 |
| PDF | WeasyPrint (HTML→PDF, підтримка кирилиці) |
| Фонові задачі | Планувальник у процесі backend (APScheduler) — для нагадувань і перевірки прострочень; черга (Celery/Redis) не потрібна на цьому масштабі |
| Автентифікація | Власна реалізація: JWT + TOTP (pyotp) |
| Деплой | Docker Compose, nginx як reverse proxy |

Архітектура — модульний моноліт: окремі домени (risks, compliance, audits, policies, users) у межах одного застосунку. REST API з OpenAPI-документацією — це і внутрішній контракт frontend↔backend, і майбутній публічний API.

## 6. Roadmap

### Фаза 1 — MVP (ядро)

- Користувачі, ролі (4 фіксовані), локальні акаунти + TOTP, audit log.
- Модуль ризиків: реєстр, матриця 5×5, плани обробки, heat map.
- Модуль комплаєнсу: каталог ISO 27001 Annex A, реєстр контролів, мапінг, gap-аналіз, evidence.
- Excel/CSV-експорт, базовий дашборд.

### Фаза 2 — Аудити та політики

- Модуль аудитів: планування, чек-листи, знахідки, коригувальні дії.
- Модуль політик: життєвий цикл, версіонування, погодження, ознайомлення.
- PDF-звіти (реєстр ризиків, gap-аналіз, звіт аудиту, SoA).
- Каталог NIST 800-53, кастомний каталог для українських вимог.

### Фаза 3 — Розширення

- Email-сповіщення (дедлайни, прострочення, призначення).
- Гнучкий RBAC (кастомні ролі, гранулярні дозволи).
- Публічний REST API з токенами для інтеграцій (сканери, SIEM, HR).
- Сповіщення в месенджери (Slack/Telegram).
- Англійська локалізація.
- Кількісна оцінка ризиків (опційно, FAIR-подібна).

## 7. Поза межами проєкту (out of scope)

- Multi-tenancy — система для однієї компанії.
- SSO/SAML/OIDC — лише локальні акаунти (може бути переглянуто після Фази 3).
- Управління постачальниками (vendor/TPRM), інциденти, BCM — окремі модулі поза цією специфікацією.
- Мобільний застосунок — лише адаптивний веб-інтерфейс.

## 8. Відкриті питання

1. Чи потрібен імпорт наявних реєстрів (ризики/контролі з Excel) при запуску? Якщо так — формат шаблону імпорту.
2. Точний перелік українських нормативних документів для кастомного каталогу.
3. Брендування PDF-звітів (логотип, шаблон) — надати при реалізації Фази 2.
